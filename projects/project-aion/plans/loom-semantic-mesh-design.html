On the retraction of the hard gate

Sir's reasoning is worth recording because it generalises: build the harness first and you will build the thing to fit the harness you made for testing it. That is a real failure mode, and it is the same shape as Goodhart's law arriving one step earlier than usual — not optimising to the metric, but designing the artefact to be measurable by a metric chosen in ignorance. The concession this design makes in return is that every retrieval decision is logged in full from day one, so the harness that eventually gets built has real behaviour to test against rather than a specification.

01

The proposal in one paragraph

Prompts would pass through a layer that reads them, searches local knowledge for related material — project history, related documents, guidelines, design patterns — and folds what it finds into the message before it reaches the model. The intent is a counterpart to the CLAUDE.md auto-load mechanism that is adaptive rather than fixed, and logged rather than invisible.

Short answer, unchanged from revision 1

The diagnosis is correct and the mechanism exists. There is a purpose-built, cache-preserving way to inject context mid-conversation, available today with no beta flag. The injection for interactive lanes should happen client-side in the hook layer rather than inside the gateway, because Claude Code owns the conversation transcript and the cost difference is roughly twelvefold. Loom becomes the retrieval service rather than always being the injector.

02

The problem is real, and it can be measured

Every Archon session loads a fixed set of files unconditionally. Everything else in the curated knowledge base is invisible unless someone happens to search for it.

Context the model can see, versus context that exists
The teal sliver is 42,777 bytes of always-loaded memory (~11,257 tokens) The full bar is 6,412,558 bytes across 409 Markdown files

Static memory surfaces about 0.67% of the corpus, and which 0.67% is decided in advance by hand. This is not primarily a cost problem — 11,257 tokens is about 1.1% of a one-million-token window. It is a relevance problem: the material that would help with today's task is usually not the material someone chose to pin last month.

The proof case is this document

The five Loom design documents from March — 82 KB, directly about the thing being evaluated — were surfaced by no memory tier. They were found by accident, in a grep run for an unrelated reason. Institutional knowledge existed, was indexed nowhere the model reads, and surfaced only by luck.

03

A primitive version already exists — and it is smaller than it looks

relevance-retrieval.js is one of twelve hooks on the UserPromptSubmit path. Its own header calls it "the rattlesnake reflex for memory recall". Reading it closely for this revision showed it is even thinner than revision 1 claimed, and that it has two quite different tracks.

Track 3
12 hardcoded keyword→file entriesliteral substring countingthreshold 2 hits, 1 if a questionmax one excerpt, 800 chars
Track 4
5 detectorscalls nothinginjects an instruction telling the model to searchcost lands on the next turn

Track 3 is a lookup table dressed as retrieval: best single match wins, and the winner is chosen by counting literal substrings. Track 4 is more interesting and more troubling — it does not retrieve anything. It injects text instructing the model to call the RAG search tool itself. The retrieval cost is therefore displaced onto the model's next turn, where it is invisible to the hook's own latency budget and where it may simply not happen.

Three defects in the existing reflex

.retrieval-state.json is not scoped by session — one file, rewritten on every prompt across every lane, with an unbounded mcp_injected list. Every failure path swallows to an empty output, so any error is a silent no-op. And context-health-monitor.js alongside it has its projects directory hardcoded to the old Jarvis path rather than Project_Aion, so one of its six health layers reports a number that is simply wrong here.

The infrastructure underneath is genuinely present: Qdrant with 23 collections at 2560 dimensions, Graphiti on Neo4j, an MLX embedding server, and JICM's compression cycle. What is missing is the ranking-and-injection layer that connects them to the prompt, with a budget and an audit trail.

Measured today, and it revises a standing belief

The MLX embedding server had been carrying a reputation for leaking badly. At 24 hours uptime it shows 2.50 GB resident, 2,474 MB current footprint against a 3,322 MB peak. Peak exceeding current by ~850 MB is growth-then-collection, not a monotonic leak. A 4-bit 4B model has a steady-state floor near 2.4 GB, so this is healthy. LiteLLM over the same window is flat at 290 MB. The old figure should not be repeated without re-measuring. This matters for Q18 and is taken up in §13.

04

Cache anatomy — answering Q6 and Q7 properly

The misconception first, because it is the crux

Sir asked whether "content block lookback pressure" presumes Loom is looking back through recent turns to pull context from them. It does not. Lookback is not Loom looking backward at anything. It is an internal mechanic of the server's cache lookup, and it would exist identically if Loom performed no retrieval whatsoever. Revision 1 used the term without unpacking it, which was my error.

Three facts that make the rest obvious

  1. The API is stateless. There is no session on the server. Claude Code re-uploads the entire conversation on every single turn — all 300,000 tokens of it, every time. What feels like the model remembering the conversation is the client replaying the whole transcript on each request.
  2. Prompt caching is therefore not memory. It is a receipt. The server retains precomputed attention state for byte sequences it has processed before. When the re-uploaded prefix matches one, it skips recomputation and charges 0.1× instead of 1.0×. Nothing is stored for you; you are simply not billed twice for the same work.
  3. Invalidation therefore loses no data and breaks no functionality. The conversation continues perfectly. You just silently pay roughly ten times more for that turn. That is precisely what makes it dangerous — a pure cost failure with no visible symptom.

What a breakpoint is

A cache_control breakpoint is a marker attached to one content block. It means: cache everything from the start of this request up to and including this block. The request is assembled in a fixed render order — tools → system → messages — and matching is a strict prefix comparison. One changed byte at position N invalidates everything from N onward. A maximum of four breakpoints are allowed per request.

And this is where the twenty blocks come in

To reuse a cache entry the server walks backward from the breakpoint through at most twenty content blocks looking for a prior entry to extend. Beyond twenty, it stops looking and rebuilds.

Why agentic work blows the window

Every tool_use is its own content block, and so is every tool_result. A single turn in which the model makes twelve tool calls therefore produces roughly twenty-four blocks — the window is exceeded within one turn, before any retrieval layer adds anything. This is a pre-existing condition of Aion's workload, not something a mesh creates. A mesh adding one block per turn makes an existing problem marginally worse.

The remedy is mundane and cheap: place an intermediate breakpoint roughly every fifteen blocks. Four breakpoints are available and Aion currently reasons about none of them.

The invalidation hierarchy — the load-bearing table

What changesTools cacheSystem cacheMessages cache
Tool definitions added, removed or reordered❌❌❌
Model switched❌❌❌
System prompt content edited✅❌❌
Message content appended✅✅❌

Read the bottom row and then the third row together. Ordinary conversation invalidates nothing. Only touching tools, the system prompt, or the model forces a rebuild. Injecting retrieved context into the system prompt invalidates the system cache and every message after it, on every turn — for a lane at 300,000 tokens and 99% cache hit rate, that converts a 0.1× read into a full reprocess. It is the single most expensive mistake available in this design space, and "enhance the prompt" read naively walks straight into it.

Three newer facts revision 1 did not have

  • Opus 5's minimum cacheable prefix is 512 tokens, down from 1,024 on Opus 4.8. Prompts previously written off as too small to cache now qualify. Note the minimum is not monotonic across generations — it is 4,096 on Opus 4.6 and Haiku 4.5 — so it must be read per model, never assumed.
  • Mid-conversation system messages are supported on Opus 5, Opus 4.8, Fable 5 and Mythos 5 with no beta header — but not on Sonnet 5. That exclusion matters if satellite lanes ever run Sonnet.
  • A model switch has no cache escape hatch at all — caches are model-scoped. This is a hard strike against Loom's model-routing feature for interactive lanes, and it is a much sharper argument than revision 1 made. Routing remains perfectly safe for single-shot Nexus jobs.
05

Q8 — is there "some physics" to the static memory files?

Sir asked what lies behind the recommendation to shrink Tier A "toward invariants only". There is something real there, and it is closer to economics than physics.

A byte in CLAUDE.md is not paid for once. It is re-uploaded on every turn for the entire life of the session, and it sits in the cached prefix, so it is re-read at 0.1× on every turn thereafter. Its cost is small per turn and unbounded in aggregate. More importantly, its selection is paid for once, months ago, by a person guessing what would be needed.

Static tier (Tier A)

1 × N turns

  • Cost scales with session length, not with relevance
  • Selection is fixed before the task is known
  • Zero marginal cost to read once cached
  • Every added line dilutes attention across the whole session

Retrieved tier (Tier B)

1 × 1 turn

  • Cost is paid when the material is plausibly relevant
  • Selection happens after the task is known
  • Also cached forward once injected into the transcript
  • Wrong retrievals are individually cheap and individually visible

The real asymmetry is attention, not tokens

The token arithmetic is minor at these sizes. What actually degrades is salience. A guardrail stated once among four hundred lines of pinned reference competes for attention with everything else pinned beside it, on every turn, whether or not it bears on the task. The invariants — identity, guardrails, form of address, filesystem policy — earn their place precisely because they apply unconditionally. Anything that applies conditionally is, by definition, better served by a mechanism that can evaluate the condition. That is the whole argument for the split, and it is why Tier A should shrink as Tier B becomes trustworthy — never before.

Architecture — three tiers, one service

Tier A
static invariants identity · guardrails · form of address · filesystem policy. Always resident. Shrinks only as Tier B earns trust.
Tier B
adaptive injection the UserPromptSubmit hook. Primary path for interactive lanes. Cache-safe, transcript-honest, budgeted, logged.
Tier C
Loom as retrieval service owns embedding, fan-out, ranking, caching, audit. Serves Tier B over HTTP. Injects directly only for single-shot callers.

The inversion is that Loom becomes the service, not always the injector. One implementation then serves both interactive lanes, where injection must be client-side, and Nexus jobs, where it must be gateway-side because no hook layer exists.

The new capability: reshaping tools without paying for it

Revision 1 did not know this existed. On Opus 5 and later, behind the beta header mid-conversation-tool-changes-2026-07-01, tool_addition and tool_removal blocks on a system-role message can change the available tool set without invalidating the cache, provided the tool was pre-declared with deferred loading.

Why this is more than a footnote

Look again at the invalidation table: changing tools normally invalidates everything. That single fact is why no system in Aion has ever considered adapting an Archon's tool surface to the task at hand. This beta removes the cost. A mesh that already decides "this prompt is about Qdrant ingestion" is one step away from also deciding "so surface the RAG tools and retire the browser ones". Nothing here should be built yet — it is noted because it changes what the mature form of this system could be, and because designing Tier C's response shape to carry tool hints later costs nothing today.

Q13 — is the hook-sometimes, gateway-sometimes asymmetry a maintenance problem?

It is a fair worry and the honest answer is: it would be, if the two paths held separate logic. In the proposed shape they do not.

Everything that can be got wrong — embedding, fan-out across stores, scoring, budgeting, deduplication, provenance, caching, audit — lives in one service, in one process, behind one endpoint. What differs between the two paths is only the last step: who writes the returned passages into the request.

ConcernInteractive laneSingle-shot Nexus job
Embedding, retrieval, ranking, budgetidentical — same service, same code path, same audit row
Who injectsthe hook, client-sidethe gateway, in-flight
Why it must be that wayClaude Code owns the transcript; injecting elsewhere makes the transcript lieno hook layer exists; no transcript exists to diverge from
Cache consequenceinjection enters the prefix, read at 0.1× thereafterno next turn, so caching is irrelevant
Failure surfacehook fails → prompt proceeds bare, alert raisedgateway fails → request proceeds bare, alert raised

Could the paths be unified anyway?

Yes, in one direction only: give Nexus jobs a hook layer. Nexus already forks Claude sessions through the Styx bridge, and those forked sessions do have hooks. If pipeline jobs were launched with the same hook set as interactive lanes, the gateway injection path could be deleted entirely and Loom would be purely a service. That is a genuinely attractive endgame and it costs nothing to keep the door open. It should not be attempted first, because it couples the Loom build to a Nexus refactor, and because the gateway path is the cheaper of the two to write.

Unifying in the other direction — routing interactive lanes through gateway injection to match Nexus — is the twelvefold-cost mistake. It should be named explicitly so nobody proposes it later as a simplification.

An unrelated defect this question exposed

Investigating the Styx path turned up something worth fixing regardless of Loom. The bridge exports only the tmux session and Alfred directory to forked sessions, so pipeline-forked Claude sessions are untelemetered by construction — they never inherit the proxy base URL. Separately, no settings file sets that variable, so a bare claude invocation bypasses the usage proxy entirely. Neither is a Loom problem. Both mean the current telemetry picture has holes in it that any future measurement would inherit.

Q15 — the routing layer, and why it has to be built rather than configured

Sir asked whether something tells Loom which stores to search and which tags to filter on. Today, nothing does, and the reason is structural:

There is no payload filtering on retrieval anywhere in the RAG server

Qdrant's filter primitives are imported, but they are used only for deduplication and deletion. Neither search path passes a query filter. Isolation today is by collection, and by nothing else. The payload written at ingest carries text, source, chunk index, hashes and file metadata — and no Archon field, no lane field, no tag field. The one exception is that JICM's auto-ingest writes a session_id, which is the single field that could support per-session or per-Archon filtering today. No search path reads it.

So the routing layer has a real choice to make, and it should be made deliberately:

Route by collection

works now

  • Zero schema change; the multi-search tool already accepts a collection list
  • Hard isolation — an Archon cannot read what it was not pointed at
  • Coarse: a new axis means a new collection, and collections multiply
  • Cross-cutting queries need explicit fan-out

Route by payload tag

needs a field

  • Add archon, lane, scope and tier at ingest
  • Soft, composable isolation — one store, many views
  • Enables the thing Sir actually asked for: core best-practice memory always reachable, Archon-specific memory elevated
  • Requires backfilling existing points, or accepting untagged legacy

Recommendation: both, in that order

Ship the routing layer reading collections first, because it works against the system as it stands today and needs no migration. Add the payload fields at ingest immediately — from the first line of enrichment code — so that tagged data starts accumulating while the collection-based router is in service. Filtering by tag then becomes a change to a query, not a data migration. The mistake would be to design for tags and be unable to ship until Qdrant is backfilled.

The shape Sir described — core behavioural memory retrievable by everyone, Archon-specific knowledge elevated — is then expressible directly as a scored blend: search the shared jarvis-context tier and the requesting Archon's own tier, and apply a modest score premium to the Archon's own material rather than excluding the shared tier. Elevation by weighting, not by walling off. That also degrades gracefully for a brand-new Archon with an empty store, which walling off does not.

Q14 — does this quietly replace deliberate memory retrieval?

This is the sharpest question in the set, and the concern is justified. A reflex that always fires does tend to displace the deliberate act it resembles. The answer is that the two must be separated by construction, not by discipline.

Reflexive (Tier B)Intentional (MCP search)
Who initiatesthe hook, before the model sees the promptthe model, mid-reasoning, as a tool call
What it optimisesbreadth — "here is what may bear on this"depth — "I need the answer to this specific question"
Querythe user's prompt, unmodifieda query the model composed deliberately
Budgetbounded per turnbounded by the model's own judgement
Failure modedilution — irrelevant material crowds the windowomission — the model does not think to look
Marked in context asprovenance-tagged, scored, attributedan ordinary tool result

They fail in opposite directions, which is exactly why keeping both is right. The reflex covers the model's blind spot — not knowing what it does not know to ask for. The deliberate call covers the reflex's blind spot — the query the prompt's surface form does not express.

Three concrete guarantees against displacement

  • Reflexive material is labelled as such, always. Every injected passage carries its score, its source path and the fact that it arrived unbidden. The model can then discount it. Unlabelled injection is what would make deliberate search feel redundant.
  • The reflex never answers a question — it only offers material. Its output is passages with provenance, never a synthesised claim. A summary would displace enquiry; a citation invites it.
  • Instrument the interaction rather than assuming it. Log, per turn, whether an injection occurred and whether the model subsequently issued a deliberate search. If deliberate searches collapse once the reflex is on, that is a measurable regression and a reason to redesign — not an efficiency to celebrate. This is one of the data-gathering hooks Sir asked to retain in Q24.

There is also a defect to fix in the current arrangement, which bears directly on this question. Track 4 of the existing hook does not retrieve — it instructs the model to retrieve. That is precisely the confusion of the two modes: a reflexive trigger wearing the costume of a deliberate act, spending the model's turn rather than the hook's. In the proposed design the reflex retrieves for itself, and the deliberate path is left to the model alone.

Q10, Q11, Q12 — freshness, bloat, and bad knowledge

These three are one problem viewed from three angles, and the current ingestion path answers none of them. It is worth being precise about what exists, because the gaps are specific.

What ingestion actually does today

Trigger
the JICM actuator, at clear time. not cron not launchd no repo sweeping
Input
exactly one file — the compressed checkpoint for that lane
Dedup
embeds the first 500 characters only, top-1 query, unfiltered, skips the entire ingest at score ≥ 0.92
Staleness
deletes prior points matching the same source path, then upserts
Eviction
no TTL no age pruning no reconciliation against source files

Two consequences that are not obvious from the code

Because the checkpoint path is a fixed per-lane filename, each cycle's delete-then-upsert overwrites the last. Only the most recent checkpoint per lane survives. The session store is not a history; it is a set of five current snapshots. And because dedup embeds only the first 500 characters, two checkpoints that open with the same boilerplate header will be judged duplicates regardless of what follows — a whole session can be silently discarded on the strength of its first paragraph. An ingested_at timestamp is written and never read.

Q10 — what keeps it fresh

Freshness needs to be separated into two questions that are usually conflated. Is the index aware of a change? and does retrieval prefer the newer thing?

  • Awareness. The honest answer for the document corpus is that nothing watches it. A filesystem watcher over .claude/context/** that enqueues changed paths for re-embedding is the minimum viable mechanism, and it is small. Ingest is already keyed by source path with delete-before-upsert, so re-ingesting a changed file is correct by construction — the hard part is only noticing.
  • Preference. Even a perfectly fresh index will happily return a superseded document, because cosine similarity has no opinion about time. Retrieval should apply an explicit recency term, and it should be a tunable one rather than a hidden constant. Loom's own compression module already does exactly this shape of thing — it computes an age ratio and discounts by it — so the pattern is present in the codebase to borrow.

Q11 — what keeps it from bloating

Bloat has a natural bound here that is easy to miss: the corpus is 6.4 MB of Markdown, and it is not growing quickly. Embedding all 409 files at 2560 dimensions is a few hundred megabytes of vectors at most. The store is not where bloat will come from. It will come from derived material — checkpoints, scrollback summaries, digests — which is generated automatically, forever, at a rate set by session activity rather than by human authorship.

So bound the derived tier, not the authored one

  • Authored documents — the 409 files — need no eviction policy. They are bounded by human effort and they are the material most worth retrieving.
  • Derived artefacts need a retention policy from day one: an age horizon, a per-lane cap, or both. The current implicit policy, "keep exactly one per lane forever", is a policy by accident rather than design, and it discards history that would be valuable.
  • Read the payload before deciding. The March quality-signal document already specifies a retention floor and banded scoring for training captures. The same banding applies cleanly to retrieval material and should be reused rather than reinvented.

Q12 — what prunes or corrects bad knowledge

This is the one with no existing answer at all, and it is the most important of the three, because a retrieval system that surfaces a confidently-worded wrong thing is worse than one that surfaces nothing.

Three distinct kinds of "bad" need three distinct mechanisms, and conflating them is why this problem usually goes unsolved:

KindExample from this workspaceMechanism
Superseded — was true, now falsethe MLX leak figure in §03; the "Loom captures no cache tokens" claim in §00Recency weighting plus an explicit supersedes link. Cheap, and the corpus already uses this idiom in prose.
Wrong on arrivala checkpoint that hallucinated a task, as happened to this very session's checkpointNeeds human or model signal. The March quality-signal weights are directly reusable — human disagreement is already the heaviest negative weight in that scheme.
Misleading in context — true but wrong to surface herea DwarfCron gotcha retrieved during infrastructure workNot a correctness problem at all. This is the dilution problem, and it is answered in §17, not here.

The cheapest correction channel already exists

Corrections are already captured — there is a hook that writes them and an append-only corrections log on disk. Nothing reads it back into retrieval. Wiring corrections in as a negative signal against retrieved passages closes the loop with material the workspace is already producing. That is a far better first move than building a curation UI, and it directly serves Q24's request to retain data-gathering opportunities.

Q18 — memory footprint, and a correction to the standing belief

The measurement in §03 matters here: at 24 hours, the embedding server is flat-with-collection at 2.5 GB and LiteLLM is flat at 290 MB. The leak reputation is not supported by today's numbers, and the recent kernel panic — which had been loosely associated with memory pressure — was root-caused to a logging watchdog with zero swapouts and 93 GB free. Memory was ruled out from the panic's own stackshot.

That does not make the design question moot. It relocates it:

  • Do not add a resident process if an existing one will do. The embedding server is already running and already loaded. Loom should call it rather than embed anything itself.
  • Bound every cache explicitly at creation. Loom's compression cache is keyed by content hash and age ratio — a good shape, but a shape with no natural ceiling. Enrichment caches must be given one.
  • Measure footprint, not resident size. The 850 MB peak-over-current gap in the embedding server would read as a leak from resident size alone. Growth-then-collection and a true leak look identical unless you watch the right instrument over a long enough window.

Q4, Q5, Q19, Q21 — failure, alerting, and the deliberate absence of latency controls

Q19 accepted, and it is the right call

Revision 1's hard 300 ms budget is withdrawn. Building latency controls before there is latency data means encoding a guess as a constraint, and then measuring the system's compliance with the guess rather than its actual behaviour. The system runs at the pace it runs. What replaces the budget is not nothing — it is instrumentation: every retrieval records its wall-clock time, per store, per stage. When latency work eventually happens it will start from a distribution rather than an intuition.

One caveat worth stating plainly, since it is the cost of this choice: the Graphiti path takes twenty to thirty seconds. Running it synchronously on the prompt path will be felt immediately, on every prompt. The design response is not a timeout but a structural one — Qdrant is fast enough to be synchronous, Graphiti is not, so Graphiti results land as an asynchronous follow-up rather than blocking. That is a pipeline shape, not a latency control, and it survives Q19 intact.

Q21 — how alerts are raised, through what channel, to what effect

Aion already has an alerting path, and the right answer is to use it rather than invent one. The JICM watcher delivers alerts into the W0 inbox through the inbox script with nudging suppressed, and it uses a circuit breaker — at most three fires per hour, per key — to keep a persistent fault from becoming a persistent nuisance. That is the mechanism the mesh should adopt wholesale.

What an alert must and must not do

Per the No Silent Degradation guardrail: a failed enrichment alerts and the prompt proceeds bare. It does not block the prompt — refusing to serve the user because a retrieval layer is unavailable would be a worse failure than the one being reported. But it must never be quiet, and it must never be counted as a success. The distinction that matters is that a degraded turn is a visible defect that stays open, not a fallback that closes the incident.

Concretely: alert into the W0 inbox, rate-limited by the existing breaker; record the failure on the audit row so it is countable after the fact; and surface a running failure count on the dashboard. Three channels, three different latencies of attention — immediate, forensic, and ambient.

The guardrail is currently violated by our own launcher

Grounding this answer surfaced a live instance of exactly the pattern Q21 is asking about. If the usage proxy's health check fails at launch, the launcher unsets the base URL and every lane launches straight to the upstream API. Sessions work perfectly. Telemetry stops entirely. Nothing alerts. That is No Silent Degradation violated by Aion's own code, and it should be fixed regardless of whether Loom is ever built — not least because every future measurement of this system would silently inherit the gap.

Q16, Q17, Q25 — telemetry, tunability, compression, and the knock-on benefits

Q17 answered first: enrichment does not sideline the rest of Loom, because most of the rest is already built

The worry was that reflexive context enrichment would crowd out compression, telemetry, transparency and user tuning. Reading loom-oss closely, the opposite is true — those parts exist and enrichment is the part that does not. There is a working extractive compression engine, a real DLP scanner with configurable rules, a twelve-page React dashboard served from the gateway itself with no separate service, live configuration through a PATCH endpoint that takes effect without a restart, and a per-request header override. Enrichment is the missing feature in an otherwise furnished house.

Q16 — the Pulse message-size chart, and a correction that changes its meaning

Sir noted that Pulse already plots message size, that it is interesting, and that nothing consumes it. Two things need saying, and the first inverts the chart's meaning.

The chart plots input plus output tokens and excludes cache reads

For a lane running at 99% cache hit rate, the plotted number is the uncached remainder — a few thousand tokens — while the real prompt is 300,000+. So the chart is not showing prompt size at all. It is showing cache efficiency. A spike on that chart does not mean a big prompt; it means a cache miss. That reading is considerably more useful than the one the label implies, and any decision logic built on the current interpretation would have been built on sand.

So: at what stage should enrichment assess size against the window? Not from that chart, and not from the proxy's telemetry at all — both are after the fact, and the proxy's data arrives only once the request has already been sent. The assessment has to happen in the hook, before assembly, and the hook already has the right instrument: JICM's gate computes live token totals from the transcript on every prompt, summing input, cache-read and cache-creation tokens. That number is the one to budget against, it is already computed once per prompt for other reasons, and reusing it costs nothing.

One thing the proxy is currently throwing away deserves fixing while this is in hand: the nested cache-creation object carries an ephemeral five-minute and one-hour breakdown, and the proxy stores only the flat sum. Loom-oss captures that breakdown. If any status display is showing an ephemeral percentage today, it is not coming from that database, and that should be verified rather than assumed.

Q25 — secondary benefits that come along for the ride

Token compression and cost tracking were the two already named. Grounding the codebase surfaced several more, and two of them are arguably worth more than the compression:

  • A DLP scanner across all Archon traffic. Redaction rules for keys, tokens, cards and identifiers, runtime-editable, tested on the streaming path. Given that this workspace is a public repository with a live credential store, a redaction layer between the Archons and the wire has standalone value. It is also the answer to revision 1's open question about OAuth appearing in audit logs — the mechanism exists and is configurable.
  • A complete request audit with routing rationale.   • Reconciliation against the provider's own usage reporting, which is a correctness check on our telemetry that Aion does not currently have in any form.
  • A twelve-page dashboard served by the gateway process itself, requiring no additional service to run or maintain.
  • The March training-capture design becomes viable again. Its schema, quality-signal weights and curation gates were written against an executor's internals and stranded there. An audit layer that sees every request is a better foundation than the shell functions those documents specified.

Two claims that cannot be made yet

Compression savings and session tracking currently report zeros — the documentation states plainly that per-request savings are not yet recorded pending parity work. Neither is a defect; both are features that would be badly mis-sold if quoted as working.

Q20, Q22, Q24 — non-determinism, and gathering data without building a harness

Q24's instruction shapes this whole section: build first, observe, then hypothesise. So what follows is not an experimental design. It is a list of what must be recorded from the first day so that experiments are possible later, which is a genuinely different thing and a much smaller commitment.

Q22 is the most scientifically interesting question in the set

Sir is right that the variance introduced by context enrichment is worth studying in its own right. It is also the thing most likely to be quietly lost: once enrichment is on, the same prompt yields different context, so every subsequent measurement of the system is measuring a moving target. Unless the movement is recorded, it is not merely unmeasured — it becomes unmeasurable retrospectively, because the inputs are gone.

The record that makes later analysis possible

Per enrichment, keyed by request identifier and joinable to the proxy's telemetry row:

The one design property worth protecting now: replayability

If the candidate set and scores are recorded, then a past turn can be re-scored under a new ranking policy without re-running the model. That single property converts an unfalsifiable system into one where a year of accumulated real traffic can be replayed against any future hypothesis, offline and at no API cost. It costs almost nothing to build in on day one and is close to impossible to retrofit, because the candidate sets were never kept.

This is what "retain focus on data-gathering opportunities" translates to concretely. Not a harness — a record complete enough that any harness built later has something real to run against.

Q20 accepted. Start with a generous relevance range and no hard floor. The thing that makes this safe rather than reckless is the passage-count and token budgets: with a generous score range, the ceiling on how much material can arrive is what prevents dilution, not the floor on how good it must be. The floor can then be discovered from the recorded distribution rather than guessed in advance. Note that these two controls are not interchangeable — a floor filters by quality, a ceiling filters by volume, and it is the ceiling that bounds the failure mode the dog question is about.

Q1 — quarantining the build without losing the Archon feel

The requirement has two halves in tension: minimal blast radius, but a real Archon environment rather than a toy. The good news is that Aion's lane architecture already provides most of the isolation, and it does so at launch time, which is the property that makes it trustworthy.

Isolation that already exists per lane

Process
one tmux window, one Claude process, its own working directory
Semantic
its own Graphiti group and Qdrant collections, set by environment at launch
Write scope
Graphiti enforces cross-group writes at a single point, keyed off the launch environment — a lane cannot write outside its group
Context
its own JICM registry entry, thresholds, checkpoint and scratchpad
Tools
its own MCP config, passed explicitly per lane

The recommendation: a real Archon lane, not a sandbox

Create a Loom lane exactly as Urist, Genie and Jacques were created — its own window, its own Graphiti group, its own collections, its own JICM registry entry, its own MCP config. This gives the full Archon experience because it is the full Archon experience, and it inherits the isolation properties above by construction rather than by convention. Adding a namespace requires no schema change anywhere — one environment variable, and the Graphiti server resolves the rest.

Do this in preference to a separate repository or a container. A separate repo would sever the thing that makes the work valuable, since per Q23 the Aion codebase is the subject matter. A container would isolate the filesystem, which is not where the risk lives.

Where the blast radius actually is

Worth being precise, because the intuitive answer is wrong. The risk is not that Loom code damages files — that is what git is for. The three real exposures are:

  • Shared mutable state. Qdrant and Neo4j are shared services. A Loom lane writing experimental vectors into jarvis-context would pollute the store every other lane retrieves from. Mitigation: dedicated collections and group from the start, never the shared ones. This is configuration, and it is the single most important isolation decision.
  • The prompt path. The moment enrichment is wired into a hook, it affects that lane's every prompt. Mitigation: enable per lane, and make the switch live rather than launch-time so a bad rollout is reverted in seconds rather than requiring a restart.
  • Hook registration semantics. This one has bitten repeatedly and deserves stating: a hook's script body is live immediately, but its registration is only picked up at session start, and MCP or permission changes need a full restart. So an experimental hook that appears inert may become live for every lane at the next clear. Mitigation: register the enrichment hook in the Loom lane's own settings, never in the shared set, until it has earned promotion.

For the service itself, Loom's own defaults suit staging well without modification: SQLite storage by default, no provider keys stored, and localhost binding with no authentication assumed. A staging instance is genuinely inert until a lane is pointed at it.

Q2 — Watcher, JICM, and how a mesh interacts with them

First, an ambiguity that causes real confusion

"Watcher" names two different things. The daemon is a 1,358-line script running under launchd, polling every five seconds, and it is the thing that actually acts. The console is a tmux window showing a read-only dashboard. They are not the same process and the dashboard does nothing. There are two further watchers besides — a Jarvis watcher and a cost-anomaly watcher, both separate again. Any statement about "the watcher" should say which.

The cycle, as a sensor–signal–actuator loop

1 Measure
the JICM gate hook, on every prompt. Canonical source is the transcript, not the status line. Tokens = input + cache-read + cache-creation. Carries the previous value forward if usage is unreadable — never zero.
2 Decide
soft 300,000 / hard 330,000 absolute tokens, with per-lane overrides. Burn rate and estimated time to each threshold computed alongside.
3 Signal
the Stop hook writes a clear-now signal file for that lane key
4 Fire
the daemon validates — live raiser, occupies the pane, still over threshold — then spawns the actuator, double-gated
5 Actuate
wait for idle, ask the session to flush to scratchpad, refuse to clear without a non-empty anchor, write a lineage edge, fold in a transcript digest, then inject the clear
6 Compress
two tiers — fast extraction, then a local narrative model
7 Ingest
the checkpoint goes to Qdrant; a parallel path goes to Graphiti

Where a mesh helps JICM

  • It closes the loop JICM leaves open. JICM already writes checkpoints into the semantic store on every clear. Almost nothing reads them back — the restoration path reads the checkpoint file, not the store. A retrieval layer makes years of accumulated checkpoints reachable by relevance instead of by recency. The producer exists and the consumer does not; the mesh is the missing consumer.
  • It makes post-clear restoration semantic rather than positional. Today a cleared session gets its own most recent checkpoint. With retrieval it could get the checkpoints, from any lane and any date, that bear on what it is about to do.
  • It reduces the pressure that drives clearing. Retrieval on demand is a substitute for keeping material resident, and resident material is what drives the token count toward the threshold.

Where they genuinely conflict, and it must be designed for

Injection inflates the number that triggers compression

The gate counts everything — input, cache reads, cache creation. Injected passages enter the transcript, so they count. Enrichment therefore accelerates the arrival of the clear threshold, and a lane with aggressive retrieval will clear more often than the same lane without it. That is not a bug to suppress; it is a real resource being consumed. But it must be visible: injected tokens should be attributable in the gate's accounting, so that a lane clearing twice as often is understood as a consequence of its retrieval budget rather than a mystery.

There is a second-order effect worth naming. More frequent clears mean more checkpoints, which means more ingested material, which means more retrievable context, which means more injection. That is a feedback loop, and while it is slow and mild, it is the same shape as the runaway the dog question is about — see §17.

One further interaction is favourable and worth exploiting. The clear cycle already produces a compressed narrative of the outgoing session using a local model, and already folds in a transcript digest. That machinery is a ready-made summarisation resource for retrieval material, running locally at no API cost. Retrieval should reuse it rather than building a parallel summariser.

Q3 — the two ports. Do not merge them.

Three grounded reasons, and the question is far from irrelevant — getting it wrong later would be expensive to undo.

Port 9800 — the observer

stays in-path

  • Contract is explicit: observes, does not modify
  • Three deliberate exceptions, all mechanical — header stripping, encoding rewrite, response header allowlist. Body relayed verbatim.
  • Captures cache read and cache write tokens today
  • Writes to Postgres with conflict-safe inserts

Port 4444 — the mutator

sits beside the path

  • Rewrites request bodies by design — that is its purpose
  • Compresses, enriches, routes, redacts
  • Genuinely free: nothing listens on it, no config binds it
  • Serves the hook over HTTP for interactive lanes

The decisive argument is the second one. An observer's value comes entirely from the guarantee that it does not modify. Chaining a mutator behind it destroys that property permanently and quietly — every future question of the form "did the proxy see what the client sent?" becomes unanswerable. Two processes, two roles, one of which can be trusted absolutely.

Revision 1 offered a third reason that has to be withdrawn: that Loom's audit lacks cache fields and would therefore blind telemetry. That was wrong. Loom-oss captures the split end to end and even records the ephemeral breakdown the proxy discards. The argument against merging does not need it and is stronger without it.

Topology: Loom sits beside the path as a retrieval service that the hook calls; the proxy remains the only thing in-path. Loom goes in-path only for single-shot Nexus jobs, which do not traverse the proxy anyway — which is itself a telemetry gap worth closing separately, per §07.

The dog — designing a reflex that terminates

The allegory does more work than it first appears to, and the reason is in what the two scenarios hold constant. Same person, same dog, same childhood memory, same pleasantness, same associative cascade. The retrieval is identical in both. Only the aim differs. In one case the aim is focus, and the memory is a defection from it. In the other the aim is diffuse and prosocial, and the same memory fulfils it.

The consequence is uncomfortable for the whole design

Semantic similarity measures the relation between a passage and a prompt. In both scenarios that relation is unchanged. No embedding model, at any quality, can tell the two scenarios apart, because the difference is not in the material and not in the prompt — it is in the goal, which is nowhere in the input. Improving the retriever cannot fix this. The information required is simply absent.

That is the single most important thing this question exposes, and it means relevance has to be modelled as a three-way relation — passage, prompt, and aim — rather than the two-way relation every retrieval system defaults to.

The pathologies, translated into mechanisms

Sir's list is not metaphorical. Each named condition has a specific, buildable failure mode, and — usefully — a specific structural prevention. The distinction that matters throughout is that these are prevented by construction, not by tuning. A threshold can always be set wrong. A loop that cannot form cannot form.

PathologyThe mechanism that would produce itStructural prevention
Rumination — the unending chain of context-grabbing Retrieved passages are themselves used as retrieval queries. Each hop is locally reasonable; the chain diverges. One hop, always. Retrieval never feeds retrieval. The query is the user's prompt and nothing else, ever. This is not a budget — it is an absence of the edge that would make a cycle possible.
Hyperfixation — the same material, every turn, forever Injected text enters the transcript, so next turn's context resembles it more closely, so it scores higher, so it is injected again. A genuine positive feedback loop. Embed the user's prompt only — never the transcript, never prior injections. The loop's return path is severed. Add a refractory period: a source recently injected is suppressed for a few turns. This is habituation, and it is what a healthy nervous system does with a repeated stimulus.
Phobia and avoidance One heavily-weighted document dominates an entire trigger class — every mention of a word drags in the same incident report, indefinitely. Cap per-source dominance within a turn, and require diversity across the selected set. One source may not supply the whole budget. Decay the weight of material that is repeatedly surfaced and never acted upon.
Decision paralysis Too many plausible passages, none decisive; the model spends its turn adjudicating context rather than working. A hard ceiling on passage count — the volume control from §13. Note this is the ceiling, not the floor, and it is why the generous relevance range Sir asked for in Q20 is safe.
Dissociation Retrieval fails silently; the model reasons from context that was never delivered, and the transcript records conclusions without inputs. Alert on failure, per §11. This is also precisely the transcript-divergence problem from §07 — the same defect arriving by two different routes.
Intrusive recall Material arrives with the same authority as the user's own words, and cannot be discounted because its origin is invisible. Provenance on every passage, always. Score, source, and the fact that it arrived unbidden. Unlabelled context is indistinguishable from instruction — which is the prompt-injection problem and the psychological one having the same root.

The organising principle: a healthy reflex terminates

Sir's own contrast contains the answer. The rational response to the mouse is surprise, recognition, rational reaction — three steps, and then it is over. The pathological response is characterised not by having been triggered but by failing to terminate. Fear, cascade, paralysis, and no exit.

So the design target is not a cleverer reflex. It is a reflex that is terminating by construction: one hop, bounded volume, habituating on repetition, labelled at delivery, and structurally incapable of triggering itself. Given those five properties, a badly-tuned retriever produces irrelevant context — which is annoying and visible and cheap. It cannot produce a spiral, because there is no path along which a spiral could propagate.

The aim problem, and what can honestly be done about it

The jog-versus-park distinction still needs answering, and it cannot be answered by retrieval quality. Three approaches, in increasing order of ambition and decreasing order of confidence:

  • Inherit the aim from the lane. Weak but free and available immediately. An Archon lane already is a declared purpose — that is the entire point of the cloning programme. Urist's aim is the fortress; Genie's is its project. Per-Archon store routing (§08) is therefore already a partial aim signal, arriving as a side effect of work that is happening anyway.
  • Let the session declare its mode. A focused mode and an exploratory mode, differing in budget and in how much associative distance is tolerated. This is the jog and the park, made explicit rather than inferred. It is honest about the fact that the system cannot know the aim, and asks. It is also the only one of the three that would have distinguished Sir's two scenarios reliably, because the information genuinely lives with the person, not in the scene.
  • Infer the aim from trajectory. Recent turns do carry evidence of whether the session is converging on a task or ranging across one. Attractive, and it should be recorded (§13) long before it is acted upon — inferring aim badly is worse than not inferring it, because it produces confident misdirection rather than mere noise.

And one thing the system already has that a person does not

The jogger cannot decline the memory — by the time it has surfaced, the focus is already broken. An Archon can. Retrieval offers material with provenance; the model decides whether it bears on the task and may disregard it in a sentence. The reflex is genuinely reflexive, but the response to it is not.

This is why §09's separation matters so much and why provenance is load-bearing rather than decorative: it preserves the step the pathological cases lack. Retrieval proposes. The model disposes. The failure mode to fear most is not retrieving the wrong thing — it is retrieving the wrong thing in a way that cannot be recognised as retrieved, because that is the one case where the deliberating step has nothing to work with.

Verdict

The diagnosis is right. Static memory surfaces under one percent of the corpus by a selection fixed in advance, and this document's own subject matter was surfaced by accident rather than by any memory tier.

The mechanism is right. System-role messages appended to the messages array are cache-preserving and injection-safe. They are purpose-built for this.

The placement needs one inversion. Loom is the retrieval service; injection for interactive lanes stays client-side in the hook, because Claude Code owns the transcript and the cache economics differ by roughly twelvefold. Loom injects directly only for single-shot callers, which have no hook layer and no transcript to diverge from.

And the dog question changes the design more than the other twenty-five combined. Relevance cannot be a two-way relation between a passage and a prompt, because the two scenarios differ in neither. The reflex must instead be built so that it terminates — one hop, bounded volume, habituating, labelled, and structurally unable to trigger itself — and so that the deliberating step above it always retains the ability to decline what it is handed.

The argument for building it

Not token savings; those are marginal, and on this codebase they are currently unmeasured and reported as zero. It is that a system whose institutional memory is 150 times larger than what it can see has a specific, addressable defect — and every piece of infrastructure needed to fix it is already running on this machine. What this revision adds is that the same investigation found eight silent defects in that infrastructure, which is itself an argument for the work: the mesh cannot be built without first making the system it retrieves from tell the truth.
