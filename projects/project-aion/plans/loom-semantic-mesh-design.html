Project Aion · Design Analysis · No implementation

Loom as a Semantic Mesh

An assessment of the proposal to route prompts through Loom so they collect semantically related context from local knowledge layers before reaching the model — measured against what Aion already runs, and against how prompt caching actually works.

2026-08-27 verdict: build it, with one inversion 6.4 MB reachable vs 42 KB loaded cache economics decide the design
01

The proposal in one paragraph

Prompts would pass through Loom on their way to the model. Loom reads the prompt, searches local knowledge layers for related material — project history, related documents, guidelines, design patterns — and folds what it finds into the message. The enriched prompt is cached and sent upstream in place of what was typed at the terminal. The stated goal is a counterpart to the CLAUDE.md auto-load mechanism that is adaptive rather than fixed, and logged rather than invisible.

Short answer

The diagnosis is correct and the mechanism exists. There is a purpose-built, cache-preserving way to inject context mid-conversation, and it is available today with no beta flag. But the injection should happen client-side in the hook layer, not inside the gateway — because Claude Code owns the conversation transcript and the cost difference is roughly twelvefold. Loom becomes the retrieval service rather than always being the injector. Section 5 shows the arithmetic.

02

The problem is real, and it can be measured

Every Archon session loads a fixed set of files unconditionally. Everything else in the curated knowledge base is invisible unless someone happens to search for it. Measured on this workspace today:

Context the model can see, versus context that exists
The teal sliver is 42,777 bytes of always-loaded memory (~11,257 tokens) The full bar is 6,412,558 bytes across 409 Markdown files

Static memory surfaces about 0.67% of the available corpus, and which 0.67% is decided in advance by hand. That is the actual defect. Note carefully that this is not primarily a cost problem — 11,257 tokens is roughly 1.1% of a one-million-token window, which is negligible. It is a relevance problem: the material that would help with today's task is usually not the material someone chose to pin last month.

This session produced a textbook example of the failure

Five Loom design documents totalling 82 KB — directly relevant to evaluating Loom — sat in alfred/.claude/context/systems/ the entire time. No memory tier surfaced them. They were discovered by accident, during a grep run for an unrelated purpose. A semantic layer keyed on the word "Loom" would have surfaced them in the first second of the task. That is the whole argument in one incident: the knowledge existed, was indexed nowhere the model reads, and appeared only by luck.

03

A primitive version already exists

This idea is not new to the workspace. A hook called relevance-retrieval.js is already registered on every prompt, and its own header describes it as "the rattlesnake reflex for memory recall." It has the right shape and the wrong engine.

Eight hundred characters is 0.012% of the corpus per prompt. The hook is a lookup table wearing the costume of a retrieval system. Crucially, though, it is already wired into the right place in the request lifecycle — which turns out to matter enormously, for reasons the next two sections make clear.

04

The technical crux: how prompt caching actually works

This section decides the architecture. It is not a matter of taste or preference — it is arithmetic, and getting it wrong is the single most expensive mistake available in this design space.

Prompt caching is a prefix match. The system hashes the request from the beginning up to each cache breakpoint. Any byte that changes anywhere in that prefix invalidates everything after it. The request is assembled in a fixed order, and that order is what makes injection position so consequential:

The mistake the naive reading walks straight into

Read the edit system row again. Injecting retrieved context into the system prompt destroys the system cache and every message after it — on every single turn. Genie is currently running 234,000 tokens at a 99% cache hit rate; Jacques is at 335,000 tokens, also 99%. Cached reads cost roughly 0.1× the base input price. Losing the cache means reprocessing the entire conversation at full price, every turn — an input-cost increase of about tenfold, with no error message and no visible symptom other than the bill.

The mechanism that makes this safe

There is a purpose-built escape hatch, and it is available today on Opus 5, Opus 4.8, Fable 5 and Mythos 5, with no beta header required:

Append a system-role message to the messages array

Instead of editing the top-level system field, append {"role": "system", "content": "…"} to messages[]. Because it sits after the cached history rather than before it, the entire cached prefix survives untouched. This is exactly the shape a semantic mesh needs.

There is a second property that is easy to overlook and matters just as much:

It is also the prompt-injection-safe channel — and retrieval makes that essential

Text placed inside a user turn can be forged by anything that writes to user-visible input. Retrieved documents are precisely that. A semantic mesh takes third-party file content and places it into the prompt; if that content lands in a user turn, then any retrieved file can impersonate the operator and issue instructions. The role: "system" channel cannot be spoofed from content. This is not a nicety — it is the difference between a retrieval layer and an injection vulnerability.

Two more constraints worth knowing before designing

  • Four breakpoints maximum per request, and the minimum cacheable prefix on Opus 5 is 512 tokens — short injections will not cache at all, silently.
  • A twenty-block lookback window. Each breakpoint searches backwards at most twenty content blocks to find a previous cache entry. Agentic loops already emit many tool-call and tool-result blocks per turn; adding an injected block each turn eats into that budget and can push a breakpoint out of range, producing a total cache miss that nothing reports.
05

Why the gateway is the wrong place to inject

Loom sits at the /v1/messages boundary. By the time a request arrives there, Claude Code has already assembled everything — the system prompt, the CLAUDE.md imports, the tool definitions, the entire conversation history, and the new user turn. This creates one decisive asymmetry:

Claude Code owns the transcript. Loom does not. Anything Loom adds in flight never becomes part of the client's record of the conversation. Three consequences follow.

Consequence one — injected tokens are paid for and never reused

Gateway injection

1.25× · forever

Every injected token pays the cache write premium and is never read back, because the next request from the client does not contain it.

  • 3,000 tokens injected per turn
  • ≈ 3,750 token-equivalents written
  • 0 tokens read back
  • Repeats identically every turn

Client-side injection

0.1× · thereafter

The content enters the transcript, becomes part of the stable prefix, and is served from cache on every subsequent turn.

  • 3,000 tokens injected once
  • ≈ 3,750 token-equivalents written once
  • ≈ 300 token-equivalents per later turn
  • Amortises across the conversation

The same content costs roughly twelve times more when delivered from the gateway than when delivered from the hook. That figure is not a modelling assumption; it falls directly out of the published 1.25× write and 0.1× read multipliers.

Consequence two — the transcript develops holes

The model's replies would reference context that the client never recorded. JICM then compresses a transcript with gaps in it, so checkpoints and scrollback summaries describe reasoning whose inputs are missing. After a /clear and restore, the conclusions survive but the evidence for them does not. This interacts badly with a system whose entire premise is careful context preservation.

Consequence three — lookback pressure

An extra content block per turn consumes part of the twenty-block lookback window described in section 4. In tool-heavy agentic loops this can silently push a breakpoint out of range.

Where the gateway is exactly right

Single-shot calls have no conversation state to diverge from. Nexus jobs, cron dispatches and headless persona runs are one request and one response — there is no transcript to keep consistent and no next turn that would have read the cache. For those callers, gateway-side injection is not merely acceptable, it is the only place it can happen, because they have no hook layer at all. This is the observation that lets one system serve both worlds.

06

Recommended architecture — three tiers

The split follows directly from the two previous sections. The central move is an inversion of the original proposal: Loom becomes the retrieval service rather than always being the injector. That single change lets one implementation serve interactive lanes (where injection must be client-side) and Nexus jobs (where it must be gateway-side).

The enrichment path runs alongside the model path, not in front of it — which avoids chaining two proxies on ANTHROPIC_BASE_URL, a configuration already recorded as breaking Chrome's classifier.

07

What it solves, adds, replaces, and touches

Problems it solves

  1. The 0.67% surfacing problem. Six and a half megabytes of curated context become reachable by relevance instead of by prior enumeration.
  2. Staleness of hand-picked selection. MEMORY.md is manually curated and capped at 140 lines. Retrieval has no such ceiling and needs no curator.
  3. Opacity. Every injection carries a request identifier, a relevance score, a source path and a reason. The current auto-load mechanism is invisible by comparison — which is precisely the complaint that motivated the proposal.
  4. Cross-lane amnesia. Urist, Genie and Jacques currently have no vector or graph access at all. An HTTP enrichment service reaches them without giving each lane its own MCP stack.

Capabilities it adds

  • Semantic ranking, where today there is only keyword matching
  • Provenance and citation for every injected passage
  • A tunable token budget, per lane and per turn
  • Content-hash-keyed caching of enrichments — Loom already has this exact shape for its compression cache

What it replaces

ComponentFate
PATTERN_TRIGGERS tableSuperseded by semantic retrieval. The hook itself survives as the injection point.
MEMORY.md link sectionThe ~40 hand-maintained pointer links are a manual index of exactly what retrieval does automatically. Should shrink toward invariants.
JICM · session-state · L1–L5Untouched. Session-level compression is a different concern from per-turn retrieval; the two compose.

New infrastructure required

  1. An /v1/enrich endpoint in Loom, returning ranked passages with provenance
  2. Relevance threshold calibration, with an evaluation harness — see section 9
  3. An injection budget policy, expressed per lane
  4. Cache invalidation when source files change (filesystem watcher bumping a content hash)
  5. A provenance format so injected passages remain attributable inside the context
  6. Metrics covering injection rate, score distribution, cache hit rate and measured outcome

09

The question nobody can answer yet

Does injected context actually improve the output?

There is no evidence either way in this workspace. Under the standing guidance on testing chaotic models, a single run cannot attribute a change — establishing this needs a fixed task set, K paired variants, and a signed-rank test, with injection on or off as the only varied factor.

Build the evaluation harness before building the retriever. Without it the mesh is unfalsifiable: it will always look as though it is working, because context is visibly present, and no one will be able to say whether the answers got better. A system that cannot fail a test cannot pass one either.

11

Verdict

The diagnosis is right. Static memory surfaces less than one percent of the corpus, by a selection fixed in advance, and this very session produced a concrete instance of the resulting failure.

The mechanism is right. System-role messages appended to the messages array are both cache-preserving and injection-safe. They are, in effect, purpose-built for this.

The placement needs one inversion. Loom should be the retrieval service; the injection point for interactive lanes stays client-side in the hook, because Claude Code owns the transcript and the cache economics differ by roughly twelvefold. Loom still injects directly for single-shot Nexus callers, which have no hook layer and no transcript to diverge from.

The strongest argument for building it

It is not token savings — those are marginal. It is that a system whose institutional memory is 150 times larger than what it can see has a specific, addressable, measurable defect, and every piece of infrastructure needed to fix it is already running on this machine.
