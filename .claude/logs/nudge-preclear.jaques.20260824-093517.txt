     - One row is one *attempt*. A task that was retried contributes more than one row for the

  ⎿  ## Planting defects

     The strongest tasks require the agent to **catch data quality problems**, not just process clean
     inputs. Plant them in the generator, spread across the trajectory, each discoverable from the
     data and none announced. Worked examples from `demultiplex-flowcell-release-001`, six across
     four milestones: an i5 orientation error in one lane's samplesheet; an index collision between
     two libraries separable only by i5; a spike-in carry-over; adapter read-through; a per-tile
     quality collapse; a patient label swap in the submitted metadata.

     Nothing is hard-coded in the reference solution. The defect, its identity and its correction are
     all *discovered from the data* — so if the data changed, the outputs would change with it. That
     property is what makes the answer key derivable rather than asserted.

     ## Output schemas

     Prefer **lighter schemas**. Each milestone pairing one fixed-column table with one free-shape
     JSON object whose structure the agent designs has worked well: the verifier searches the whole
     structure rather than demanding exact key paths. A rigid schema grades formatting compliance,
     which is not the thing under test.
